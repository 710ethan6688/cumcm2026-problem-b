# Q4 V3 架构升级测试计划

状态：已执行并完成判定。本文件保留为历史测试设计；正式采用A0（V3），A1、A2不采用，D1未继续实现。定量结果和证据边界见 [EXPERIMENT_RESULTS.md](EXPERIMENT_RESULTS.md) 与 [Q4_OPTIMIZATION_ROUTE.md](Q4_OPTIMIZATION_ROUTE.md) 第9节。

本文件只说明本轮需要实现和比较什么。具体代码组织、测试批次、参数搜索方式和本地数据划分由实现者根据现有工程自行决定。

架构原理见 [ARCHITECTURE_UPGRADE.md](ARCHITECTURE_UPGRADE.md)，结论记录在 [EXPERIMENT_RESULTS.md](EXPERIMENT_RESULTS.md)。

## 1. 测试目标

判断新增的窄角域解析覆盖及其与 V3 的联动，能否在保持全部清除的前提下：

- 降低总虚拟时间；
- 减少失败清除；
- 压缩少数不利定向源造成的长尾；
- 不明显恶化普通场景。

## 2. 需要比较的版本

- **A0：当前 V3。** 冻结基线。
- **A1：V3＋双清除终端。** 最终清除时在原 26 m 网格和解析覆盖之间选择。
- **A2：A1＋尾部决策联动。** 仅在 A1 有效后继续，尾部探测使用较低的终端兜底成本。
- **D1：第一次测向后直接解析覆盖。** 可选诊断版本，用于判断纯外部架构是否值得保留。

## 3. 实现与测试顺序

1. 保留 A0 当前运行结果和默认参数。
2. 实现解析覆盖生成器，并检查其对保守可行域的完整覆盖。
3. 接入统一代价估计和双终端选择，形成 A1。
4. 用相同本地场景批量运行 A0 与 A1。
5. 对新增模块及其直接影响的参数进行适度调优，再复测 A1。
6. 若 A1 有实际价值，再实现 A2 并重复比较。
7. 如实现成本不高，可增加 D1 作为结构对照。
8. 将结论简要写入 `EXPERIMENT_RESULTS.md`。

## 4. 自动化要求

尽量复用现有 `run_q4_batch.py`，增加版本开关并自动完成：

- 相同种子或相同场景下的版本批量运行；
- 全部完成情况检查；
- 总虚拟时间、失败清除、移动距离和测量次数汇总；
- 各版本改善、持平和退化的案例数统计；
- 失败或异常案例的日志保留。

除覆盖正确性外，不要求为本轮建立复杂的新测试框架。

## 5. 调优口径

V3 是已经调优的基线。新版本继承 V3 的公共模块和参数，允许对新增模块以及直接受其影响的尾部决策参数进行合理调优后再比较。

建议同时保留一次新模块默认参数结果和调优后结果，以区分“结构加入后的直接效果”与“最终可用版本效果”。用于作最终判断的本地案例不应全部参与参数挑选，具体划分由实现者自行处理。

## 6. 重点查看的结果

至少比较：

- 是否全部完成；
- 平均总虚拟时间；
- 最大总虚拟时间或明显长尾；
- 平均失败清除数；
- 平均移动距离；
- 平均测量次数；
- 相对 A0 的改善、持平和退化案例数。

如果新终端被选择的次数很少，还应简单记录它在哪类案例中被选择，以及是否确实减少了长尾。

## 7. 判定规则

- 不能保持全部清除或覆盖检查失败：不采用。
- 调优后仍无实际提升：不采用。
- 平均值小幅改善但最坏长尾明显恶化：原则上不采用。
- 保持全部清除，并降低平均时间或明显压缩长尾：保留。
- A1 无效：停止 A2，不再扩大改动。
- D1 即使不胜，也可作为结构对照记录，但不进入最终策略。

本轮已经完成本地配对比较，并补充了A1官方非配对观察。官方结果只用于链路与实际量级核验，不用于替代同场景因果对照。最终判定为冻结A0。
